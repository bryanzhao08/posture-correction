## Prioritized top 10 issues

Severity is for this demo validation: P1 blocks a key path or risks camera/coaching reliability; P2 affects usability/data correctness. **Observed** means reproduced in the public browser. **Code risk** means identified in source but not runtime-proven on an iPhone or the blocked later deployment.

1. **B01 — P1, observed deployment/scope blocker: the PUBLIC demo became password-gated mid-audit.** Fresh visitors see “Private beta” and no sport cards; the title remains unchanged. Pointer: `web/src/app/beta.ts:20`, `web/src/main.ts:707`. Evidence: `latest-deployment.png`, `latest-results.json`. If private beta is intentional, this is a task/access blocker rather than an implementation defect; provide test access or a stable public demo URL and rerun latest deployment.
2. **B02 — P1, observed: failed sample download has no recovery.** Abort `samples/golf_demo.json`, press sample: an unhandled `Failed to fetch` leaves “Starting…” indefinitely. End then also throws. Pointers: `web/src/main.ts:488`, `web/src/main.ts:76`. Evidence: `sample-fetch-fails.png`, `extra-results.json`. Check HTTP status/JSON, catch failures and offer retry/Home.
3. **B03 — P1, observed: End session before the sample download finishes permanently wedges the session.** Delay sample response by 3 seconds, press End immediately: `Cannot read properties of undefined (reading 'engine')`. `ended` has already become true, so later End/automatic completion cannot recover. Pointers: `web/src/main.ts:469`, `web/src/main.ts:472`, `web/src/main.ts:485`. Evidence: `early-end-sample.png`. Disable End until initialized or implement cancellation before dereferencing the session.
4. **B04 — P1, code risk: camera startup can outlive End session.** End is enabled before getUserMedia/model await completes. `stop()` cannot cancel pending startup; later `start()` installs a stream and sets `running=true`, while teardown is registered only after awaiting startup. Pointers: `web/src/app/session.ts:84`, `web/src/app/session.ts:95`, `web/src/app/session.ts:138`, `web/src/main.ts:497`, `web/src/main.ts:511`. Early End reached summary in one public run, but live-track leakage was not measured; the instrumented retest was blocked by gate. Add startup cancellation/generation checks and stop any late stream.
5. **B05 — P1, Safari code/platform risk: spoken tips may interrupt the webcam video, with no resume handling.** Speech is default-on and invoked later from frame/countdown callbacks; detection depends on changing `video.currentTime`. There is no video pause/track mute recovery. Pointers: `web/src/main.ts:232`, `web/src/main.ts:362`, `web/src/app/session.ts:100`. WebKit has a report of speech pausing getUserMedia-backed video; verify on physical iOS with speech enabled/disabled before claiming Safari works. See cited Safari section.
6. **B06 — P2, code/platform risk: private/ephemeral IndexedDB is misclassified as persistent.** `storageIsPersistent()` returns true whenever open succeeds. Safari private browsing can permit ephemeral storage, so the warning is omitted while sessions still disappear later. Pointers: `web/src/app/store.ts:77`, `web/src/main.ts:650`. Runtime storage-blocking fallback warning passed; actual Safari private mode was not tested. Show browser-local/export guidance independent of database-open success and avoid a durability guarantee.
7. **B07 — P2, observed with storage fault injection: preferences do not even last for the current visit when localStorage writes are blocked.** Select Left, then metric; re-render returns Right/imperial. Height/level/drill scoring can likewise use defaults. `setPref` catches without an in-memory preference fallback, despite its comment. Pointers: `web/src/app/store.ts:82`, `web/src/app/store.ts:91`, `web/src/app/player.ts:18`. Evidence: `blocked-storage-preferences.png`, `extra-results.json`. Keep an in-memory preference map.
8. **B08 — P2, observed: browser Back leaves the app instead of navigating its screens.** Home → Tennis does not create URL/history state; browser Back goes to `about:blank` in a fresh tab. Pointers: `web/src/main.ts:76`, `web/src/main.ts:136`. Evidence: `browser-back.png`, `extra-results.json`. Support history state/popstate so normal browser/phone navigation is predictable.
9. **B09 — P2, observed export + code: `started_at` is actually session finish time.** It is created in finish with `new Date()`; exported golf timestamps correspond to completion while duration is ~60–62 seconds. Pointer: `web/src/main.ts:480`. Evidence: both `camera-golf-*-formcoach-sessions.json`. Capture start time at session/counting start; define whether setup time belongs in duration.
10. **B10 — P2, observed: tennis camera-position explanation contradicts the selected view.** Select Groundstrokes → Side or Front; the paragraph still says “From behind…”, while the setup camera card correctly describes side/front. Pointer: `web/src/main.ts:203` (uses training-wide `tr.why` rather than selected view). Evidence: `chrome-390-tennis-groundstrokes-side.png`, corresponding desktop/front screenshots. Make the rationale follow the view or explicitly label it as the recommendation.

Additional findings: eager 7.65 MiB pose download on home is a mobile data/performance concern (`main.ts:179`); camera backgrounding automatically ends/saves the session rather than pausing (`main.ts:509`), requiring explicit UX communication; app theme meta is dark while manifest theme/background are red (`web/index.html:8`, `web/public/manifest.webmanifest:8`); profile controls are only 30–32 CSS px high and chips 40 px, below comfortable iOS 44-point targets (a comfort concern, not automatically a WCAG failure). No service worker means offline operation is untested/unavailable. IndexedDB writes resolve on request success rather than transaction completion (`store.ts:47`), so late transaction aborts are another untested durability risk. Cards reference captured canvases which may be recycled during continued capture (`session.ts:123`, `fixcard.ts:88`), so old summary still images deserve a regression check; no image-mutation failure was established in this run.

## iOS Safari-specific assessment

- **getUserMedia:** secure HTTPS context, video-only capture, muted video and playsinline are correctly present (`session.ts:86`, `session.ts:90`). `facingMode` is a preference, not proof the requested lens was chosen. No checks of resolved track settings, orientation/device changes, video pause, track ended/mute, or detection error recovery. Errors in detect are silently swallowed (`session.ts:104`), potentially freezing coaching without a message. Startup cancellation and automatic background termination are the key lifecycle risks. [Apple inline playback documentation](https://developer.apple.com/documentation/webkit/wkwebviewconfiguration/allowsinlinemediaplayback) supports the existing inline configuration requirement.
- **speechSynthesis:** feature-detected for speaking, but not primed by a direct user gesture; default-on callbacks can be subject to iOS audio policies. Potential webcam-video interruption is documented in [WebKit bug 218815](https://bugs.webkit.org/show_bug.cgi?id=218815); treat its behavior as a device/version-dependent risk, not a proven current-iOS failure. Direct `speechSynthesis?.cancel?.()` in finish also assumes the global exists (`main.ts:475`) even though speaking separately checks support. Headless Chrome did not validate audible output.
- **vibrate:** optional chaining at `main.ts:387` safely avoids a missing method. Do not depend on haptics on Safari; visual scoreboard feedback remains. [W3C implementation discussion](https://www.w3.org/2023/07/breakout_haptics_TPAC/haptics.pdf) describes adoption in Android Chrome/Firefox, rather than making it a portable iOS feedback mechanism.
- **dialog:** modern Safari supports dialog/showModal; [WebKit introduction](https://webkit.org/blog/12209/introducing-the-dialog-element/) identifies Safari 15.4 support. The direct `showModal()` call (`main.ts:527`) has no fallback for older Safari. Dialog replay/close passed Chrome; mobile Safari scroll, keyboard/focus and overlay behavior remain device checks.
- **IndexedDB/private mode:** catching failed opens and keeping sessions in memory is good. Private browsing is not equivalent to an unavailable API: [WebKit tracking-prevention documentation](https://webkit.org/tracking-prevention/) describes ephemeral private sessions. A successful open does not establish persistence; quotas/eviction also require handling ([WebKit storage policy](https://webkit.org/blog/14403/updates-to-storage-policy/)). Current warning logic and request-vs-transaction completion need improvement. No Safari-specific failure is claimed from Chrome fault injection.
